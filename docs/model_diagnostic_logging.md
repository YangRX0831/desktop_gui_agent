# 模型诊断日志说明

## 1. 目的

模型诊断日志用于记录智能体从环境感知、模型推理到动作执行和结果验证的关键过程。其主要作用是分析任务失败原因、定位动作解析问题、判断模型是否发生重复规划，以及比较不同运行之间的性能差异。

## 2. 主要记录内容

诊断记录通常包括：

- 运行编号；
- 任务相关信息；
- 逻辑步骤与尝试序号；
- 前台窗口状态；
- 截图信息；
- 感知摘要；
- 模型原始输出；
- 输出规范化结果及原因；
- 动作解析结果；
- 动作分发结果；
- 模型调用延迟；
- 状态变化与进度判断；
- 恢复信息；
- 完成判断；
- 步数预算与扩展状态；
- 异常类型等诊断信息。

## 3. 模型输出记录

为便于定位模型输出问题，决策追踪可以区分以下字段：

```text
raw_response
normalized_response
normalization_reason
parsed_action
```

例如模型输出：

```text
click(875,963)
```

系统可在满足确定性规则时将其规范化为：

```text
click(x=875, y=963)
```

同时记录对应的规范化原因。规范化结果仍需经过严格动作解析，不代表动作已经获得执行许可。

## 4. 进度与恢复记录

当动作没有带来有效状态变化时，系统会记录当前动作、是否实际分发、前后状态变化、是否存在重复动作、进度分类、重试原因和恢复提示等信息。

这些数据用于区分模型规划问题、动作解析问题、界面定位问题和控制执行问题。

## 5. 步数预算记录

当任务达到基础步数边界时，决策追踪还可记录：

- 配置的基础最大步数；
- 是否达到基础预算；
- 是否满足扩展条件；
- 是否授权扩展；
- 扩展原因；
- 剩余扩展步数；
- 实际使用的扩展步数；
- 当前有效硬上限。

## 6. 安全与隐私

诊断文件可能包含任务文本、模型响应和截图，因此应视为本地调试数据，不应直接作为公开产物上传。

调用方不得主动把以下内容写入诊断字段：

- API 密钥；
- Authorization 令牌；
- 密码；
- 私钥或其他凭据。

当前诊断写入器的职责是保存调用方提供的诊断数据，并不替代统一的秘密扫描或内容脱敏流程。手动分享日志、JSONL 或截图前仍应检查内容并完成必要脱敏。

## 7. 日志位置

主要目录：

```text
logs/agent_trace/
logs/diagnosis/
benchmark/reports/
reports/quality/
```

历史运行日志可以按需要归档或清理。版本控制仅应保留明确选择的测试结果和质量报告，不应提交完整运行日志、诊断截图或模型输出历史。
