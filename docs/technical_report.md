# Desktop GUI Agent 技术报告

## 1. 项目概述

Desktop GUI Agent 的目标是构建一个能够根据自然语言指令自主操作桌面图形界面的智能体。系统通过截取当前桌面画面、识别界面文本和窗口状态，将环境信息提交给视觉语言模型，由模型生成结构化动作，再通过鼠标与键盘控制器完成实际操作。

系统采用闭环执行方式。每一步操作完成后重新获取界面状态，并根据界面变化、任务进度和验证结果决定继续执行、重试、恢复或结束任务。

## 2. 系统总体架构

系统主要由配置与入口、智能体调度、环境感知、模型推理、动作解析、动作执行、状态验证和诊断日志等部分组成。

```text
用户任务
  ↓
命令行入口 / 配置
  ↓
GuiAgent
  ↓
桌面感知
  ↓
模型推理
  ↓
动作规范化
  ↓
严格动作解析
  ↓
安全检查与动作分发
  ↓
鼠标 / 键盘控制
  ↓
状态验证与进度判断
  ↓
下一步执行或任务结束
```

## 3. 动作协议设计

当前模型动作协议包含八类动作：

```text
click
right_click
double_click
drag
type
scroll
hotkey
finish
```

该动作集合建立在完整的鼠标和键盘控制能力之上。底层控制器还提供鼠标移动、按键按下和释放等内部原语，但这些原语不直接作为模型动作输出。

`observe` 仅保留在旧版兼容流程中，不属于当前 V3 动作协议。

### 3.1 动作输出规范

模型每次只允许输出一个动作。动作首先经过格式规范化，再进入严格解析器。

典型格式如下：

```text
Action: click(x=500, y=300)
Action: type(text="Hello World")
Action: hotkey(key1="ctrl", key2="c")
Action: finish(result="任务已完成")
```

其中 `finish` 必须包含字符串形式的 `result` 参数，`hotkey` 按 `key1`、`key2` 等顺序命名按键参数。

### 3.2 动作规范化

为了提高模型输出的兼容性，系统允许有限的确定性格式修正。例如：

```text
click(x=875, 963)
→
click(x=875, y=963)
```

以及：

```text
click(875, 963)
→
click(x=875, y=963)
```

上述转换只根据动作签名完成，不读取任务语义，也不根据截图猜测参数。规范化完成后仍需经过严格解析和安全检查。

对于当前截图中已经明确编号且能够唯一解析的元素，也支持将：

```text
click(E1)
```

确定性映射到对应元素边界框中心。

## 4. 智能体执行流程

一个逻辑步骤的主要过程为：

1. 获取当前桌面截图和窗口状态；
2. 运行 OCR 与视觉上下文构造；
3. 调用模型生成动作；
4. 对模型输出进行有限规范化；
5. 使用严格解析器解析动作；
6. 执行安全检查；
7. 分发鼠标或键盘动作；
8. 重新观察界面状态；
9. 判断是否取得进展；
10. 判断任务是否完成。

默认基础逻辑步数为 10，单步默认最多允许 3 次重试。

### 4.1 有条件的步数扩展

部分复杂任务在基础步数边界附近仍可能保持有效推进，因此系统提供有限的动态扩展机制。

扩展规则如下：

- 基础步数仍由 `max_steps` 决定，默认值为 10；
- 最多额外增加 3 个逻辑步骤；
- 每个任务最多触发一次；
- 只有最近存在可测量的有效进展时才允许扩展；
- 若存在重复动作、连续无进展、同策略重试耗尽或安全阻断，则不允许扩展。

该设计避免了简单提高全局最大步数所带来的无效模型调用。

## 5. 进度判断与恢复机制

系统在动作执行后比较前后状态，判断动作是否对任务产生有效影响。主要依据包括：

- 前台窗口是否改变；
- 截图是否发生有效变化；
- OCR 或目标状态是否改善；
- 输入焦点是否发生变化；
- 当前动作是否被重复执行；
- 是否存在连续无进展；
- 是否满足任务完成条件。

当系统检测到无进展时，会向后续模型调用加入恢复信息。对于完全相同且已经被证明无效的动作，系统可直接阻止再次分发，避免持续重复操作。

## 6. 环境感知

感知模块主要包括：

- 基于 `mss` 的桌面截图；
- 基于 PaddleOCR 的界面文本识别；
- 前台窗口和窗口列表获取；
- 感兴趣区域截取；
- OCR 与窗口信息的上下文整合。

当前真实桌面场景下的性能测量为：

| 指标 | 中位数 | P95 |
|---|---:|---:|
| 截图 | 57.88 ms | 62.17 ms |
| OCR | 2345.60 ms | 2581.18 ms |
| 总感知耗时 | 2437.33 ms | 2676.09 ms |

由此可见，当前感知性能仍未达到 PRD 中截图 ≤50ms、OCR ≤200ms 和整体感知 ≤300ms 的要求。

## 7. API 与本地模型

### 7.1 API 模式

API 模式通过 DashScope OpenAI 兼容接口完成视觉语言模型调用。

核心配置包括：

```text
DASHSCOPE_API_KEY
DASHSCOPE_API_MODEL
DASHSCOPE_API_ENDPOINT
DASHSCOPE_TIMEOUT_SECONDS
```

API 模式已经完成完整桌面任务闭环验证。

### 7.2 本地模型模式

本地模式支持 Transformers 和 OpenVINO 两种运行时。

本地模型能够完成模型加载、图像输入、动作输出、坐标转换和智能体主循环接入，但当前在真实桌面任务中的界面定位和任务规划能力仍不足，尚未达到至少 3 项简单任务端到端通过的目标。

模型目录通过环境变量配置并存放在仓库外部；Benchmark 不依赖开发机固定路径。

## 8. 诊断日志

系统记录模型调用和动作执行的关键过程，包括运行编号、逻辑步骤与尝试次数、前台窗口信息、截图信息、OCR 与感知摘要、模型原始输出、规范化结果、动作解析结果、动作分发结果、模型延迟、进度判断、恢复信息、完成判断和步数扩展状态。

诊断内容可能包含任务文本、模型输出或截图，因此只应保存在本地受控目录。API 密钥、访问令牌、密码等凭据不得作为诊断字段传入；对外分享日志或截图前仍需人工检查并脱敏。

## 9. 测试体系

项目测试分为四个层次：

1. 单元测试、集成测试和回归测试；
2. Benchmark 测试框架自检；
3. 单任务 GUI 定向测试；
4. 15 项 GUI 正式验收测试。

普通质量检查入口为：

```powershell
python -B tools/run_checks.py --all --report
```

该命令不会执行真实桌面 GUI 任务。

## 11. 当前主要限制

当前系统仍存在以下限制：

1. 复杂任务总体成功率尚未达到 PRD 70% 要求；
2. 本地模型尚未达到至少 3 项简单任务端到端通过；
3. OCR 和整体感知性能距离目标较大；
4. API 仍存在少量超过 2 秒的成功调用；
5. 注释覆盖率低于 30%；
6. macOS、Linux 和远程 CI 缺少完整实机验证；
7. 独立界面识别准确率 ≥85% 尚无充分证据。

上述限制不会改变当前代码结构和已完成测试结果，但仍属于后续优化方向。
